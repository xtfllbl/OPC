## 2. 已确认的产品范围

| 编号 | 已确认决定 | 必须保留的边界 |
| --- | --- | --- |
| D-01 | 终端支付应用直连 processor | 新交易不等待 Paywizard 建单、批准或回传成功 |
| D-02 | 终端完成交易后向 Paywizard 回传 | 支付结果与上传结果分别表达 |
| D-03 | 点击 Trans 可查当前 MID 下各终端交易 | “全部”是查询范围，不是一次下载全部历史；仅包含平台已收到的数据 |
| D-04 | B 拉取 A 的交易，由 B 直连 processor 做后续交易 | Paywizard 不代发支付，不把指令转给 A 执行 |
| D-05 | A 离线时，B 仍可处理 A 已上传的交易 | B、Paywizard 所需服务和 processor 可用，且通道支持该操作 |
| D-06 | 普通收银员可查看授权 MID 范围的交易 | 查看权限与资金操作权限分开 |
| D-07 | 有对应权限即可执行后续交易 | 保留已有操作密码要求；不因跨终端额外引入每次经理审批 |
| D-08 | 第一阶段可以查看其他终端的批次 | 只关闭本机批次，不提供远程关批或 Settle Store |
| D-09 | Paywizard 故障时，继续本机收款和本机后续交易 | 仍需 processor 可达、必要本地记录与既有支付凭据有效 |
| D-10 | Paywizard 故障时，禁止发起跨终端交易 | 已缓存或曾经拉取的他机交易也不能作为本机交易绕过限制 |
| D-11 | 后续交易目标覆盖 Refund、Void、Capture、Auth-Incremental | 按 processor、交易类型及终端组合逐项验收后开放 |
| D-12 | 终端上传批次，平台存储并提供其他终端查看 | 当前批次是最近上传快照；已关批也不等于已到账 |

本期不新增跨 MID 交易操作、远程控制 A 执行交易、门店批量关批、支付网关改造为平台代收单、无原交易退款能力扩展，或完全断网后的 Store-and-Forward 收款。已有现金、QR、Loyalty/Gift 等业务保持原流程；本期跨终端四种后续操作先按有明确通道能力的卡交易设计，不能把卡交易规则直接套到其他支付方式。

    B["终端 B：支付执行、本地记录、上传队列"] -->|"原交易引用与后续请求"| P

| 数据/行为 | 权威来源 | Paywizard 的角色 | 终端的角色 |
| --- | --- | --- | --- |
| 支付是否批准、退款是否成功、授权是否有效 | processor 的应答或查询结果 | 保存终端回传的证据，记录确认程度 | 直接请求、查询、持久保存结果 |
| 已收到的跨终端交易历史 | Paywizard 已持久化记录 | 查询、关联、聚合、权限与更新分发 | 读取展示，按需拉取 |
| 尚未上传的本机交易 | 执行终端的持久记录 | 未收到前不承诺可见或可操作 | 可靠补传，不因平台故障丢失 |
| 批次关闭结果 | processor/终端支付服务按通道确认 | 保存关批事实与明细，展示同步完整性 | 本机关批、查结果、回传 |
| 当前批次汇总 | 本机实时记录；远端为已上传快照 | 明确快照时间与数据范围 | 本机实时显示，远端标注更新时间 |
| 人员/设备可见范围 | 服务端的设备绑定与授权配置 | 限定租户、收单账户、MID 和操作权限 | 本机按有效配置执行，在线时接收更新 |

Paywizard 保存的是共享业务记录和“最新已知”状态，不是每时每刻与 processor 强一致的支付账本。列表缓存和读库不能直接作为资金执行依据。

## 4. 核心业务流程

### 4.1 本机收款与回传

1. 终端在本地生成 clientTransactionId、operationId，并在发送支付请求前持久保存请求意图。
2. 使用现有支付 SDK/原生支付服务直连 processor。
3. processor 返回后，本地事务保存结果及待上传事件；SDK 交易日志用于处理应答后、应用落盘前的崩溃窗口。
4. 立即展示真实支付结果、打印小票并允许下一笔操作，不等待 Paywizard。
5. 同步任务上传事件，Paywizard 持久化后按事件返回确认。
6. 上传超时重传相同 eventId；平台去重，终端收到确认后才标记已同步。

若 processor 结果未知，显示“结果确认中”并按通道查单；不先显示失败，也不自动新建另一笔扣款。

### 4.2 MID 交易查询

1. Trans 默认选择当前收单账户下的 MID 和 All terminals，日期建议默认为门店当地“今天”。
2. 先展示符合当前租户、MID、日期和筛选条件的缓存，标记更新时间；并合并本机未上传记录。
3. 从 Paywizard 分页获取最新记录，按统一交易 ID 去重。
4. 详情展示原交易、后续记录、来源终端、执行终端、支付状态与同步状态。
5. 最新状态仍需在操作准备和 processor 执行阶段校验；“按钮可用”不是支付成功承诺。

网络失败时保留已有缓存并明确“数据未更新”；提供 This terminal。不能静默将全 MID 列表替换成本机列表而继续显示 All terminals。

### 4.3 B 对 A 的已上传交易做后续交易

~~~mermaid
sequenceDiagram
    participant B as 终端 B
    participant W as Paywizard
    participant P as Processor
    B->>W: 获取原交易详情与可用动作
    W-->>B: 最新已知状态、版本与限制
    B->>B: 校验本地权限及配置的操作密码
    B->>W: 登记操作（operationId、动作、金额、原交易版本）
    W-->>B: 操作登记结果与绑定 B 的执行上下文
    B->>W: 标记即将执行，取得确认
    W-->>B: 执行登记确认
    B->>P: 按通道规则引用 A 的原交易
    P-->>B: 成功、明确失败或结果未知
    B->>B: 保存支付结果及回传任务
    B->>W: 幂等回传操作结果
    W-->>B: 确认已接收，更新交易链
~~~

A 不参与上述流程。原交易归属仍是 A；后续操作记录执行终端 B 和真实操作员信息（若现有系统没有个人身份，则明确仅记录设备身份，不能虚构操作员）。后续交易所属 processor 批次由通道结果决定，不自动归 A 或 B。

操作登记接口不发起支付，也不下发可自动执行的异步支付命令。平台通知只提示数据变化。

### 4.4 Paywizard 故障

| 条件 | 新交易 | 本机原交易的后续操作 | 跨终端后续操作 | 批次 |
| --- | --- | --- | --- | --- |
| Paywizard 正常，processor 正常 | 正常 | 正常，在线时尽力更新/登记 | 完成在线准备后执行 | 本机关批，远端只读 |
| Paywizard 不可用，processor 正常 | 继续直连 | 继续直连，按 processor 校验 | 禁止新发起，包括缓存的他机交易 | 本机关批并待回传；远端显示旧快照 |
| A 离线，B、Paywizard、processor 正常 | B 正常 | B 本机正常 | B 可处理 A 已上传且通道允许的记录 | 可看 A 最近上传的批次，不远程关闭 |
| processor 不可达 | 按现有支付故障流程处理 | 无法保证完成，按通道恢复 | 无法保证完成，不能因平台有记录而宣布成功 | 无法确认关批时保留结果未知 |
| B 已提交给 processor 后 Paywizard 中断 | 本机记录结果 | 保存并补传 | 当前已发出的请求继续收尾、查单及补传，不重新发起 | 同样保存真实结果 |

“故障时禁止跨终端交易”指禁止开始新的跨终端资金请求；已经发送的请求不能当成未发生，需要查明并记录结果。

### 4.5 批次上传与查看

1. 本机交易完成或批次变化时生成本机 Open Batch 快照，合并高频上传。
2. Close Batch 只作用于本机，具体交易范围和未完成预授权处理遵循通道。
3. 收到关批结果后，先保存最终批次快照和上传任务，再展示结算结果/打印 Settlement Copy。
4. 平台收到已关批摘要及明细后关联交易。明细未齐时标记不完整，不编造完整明细。
5. 其他终端查看该批次；页面展示所属终端、币种、批次号、快照时间和完整性，不展示远程关批按钮。

## 5. 一致性必须满足的约束

### 5.1 三种状态分别保存

- 支付执行状态：未发送、执行中、批准、明确拒绝、结果未知。
- 平台同步状态：待上传、上传中、已确认、需处理。
- 原交易业务状态：当前授权、累计 Capture、退款等结果的投影，来自关联操作与 processor 证据。

支付成功但平台待同步是正常可恢复状态；同步失败不能把支付改为失败。PREAUTH、CAPTURE、REFUND、VOID 与批次状态也不能合并成一个布尔字段。

### 5.2 平台锁的实际边界

Paywizard 可以串行协调 B、C 等在线跨终端操作，却无法锁住与平台失联、仍允许直连 processor 的 A。因此：

1. 平台操作登记负责在线请求去重、冲突提示、已知金额预占与结果跟踪。
2. processor 必须对原交易提供有效状态校验、可退金额等约束；两个不同请求的语义冲突，不能只靠每个请求各自的幂等键解决。
3. 状态查询只能减少陈旧，不能代替 processor 执行时的原子校验。
4. 若某通道无法保证相关约束，该通道的跨终端动作不能上线。本机可脱离平台的产品要求保持不变，不以平台锁替代通道能力证明。
5. 结果未知的操作不能因锁超时而直接释放金额、允许另一笔相同操作；需查询或人工核实证据。

### 5.3 下载记录不改变所有权

本机交易判断使用不可变的原交易设备标识及归属信息，不依据“本地是否存在一份缓存”。B 下载的 A 交易在平台故障时仍属于跨终端交易。

### 5.4 未上传数据与离线设备

本方案以终端回传为共享数据来源。A 尚未上传的记录，平台和 B 无法凭空恢复。本期不假设 processor 会直接向 Paywizard 推送记录，也不假设平台具备直接查 processor 的接口。若后续采购相关能力，应单独增加接口、认证与通道验收。

## 7. 建议实施顺序

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：契约与通道验证 | 四类跨终端操作的能力矩阵、身份/凭据、原交易字段、金额单位、并发与查单方案 | 通道证据足够；不能只拿到接口名称 |
| M1：可靠数据基础 | 本地持久记录与上传队列、平台幂等接收、原交易关联、批次快照 | 支付后断网/断电/重复回传均可恢复，金额与归属一致 |
| M2：只读共享 | Trans 全 MID 查询、统一详情、缓存降级、其他终端批次查看 | 权限、分页、未上传合并和快照标识通过 |
| M3：后续交易 | 按已通过 M0 的通道逐项开放 Refund/Void/Capture/Auth-Incremental | 原设备离线、并发与未知结果验证通过 |
| M4：试点与推广 | 终端/通道灰度、可观测性、回滚、运营说明 | 支付行为稳定；共享服务失败不拖慢本机收款 |

只读功能可先行交付。四项后续操作均在目标内，但不能把未通过通道验收的动作作为“已完成”发布。

## 8. 性能与容量建议

以下是初始验收目标，需在目标机型、部署区域和约定数据规模下测试，不是已测结果。

| 指标 | 建议目标/方法 |
| --- | --- |
| 本地按键与页面操作 | 常规交互约 100 ms 内反馈 |
| 有缓存的 Trans 首屏 | P95 不超过 300 ms |
| 正常网络最新第一页 | 端到端 P95 不超过 1 秒；冷启动单独统计 |
| 支付结果展示 | 不增加等待 Paywizard 的同步网络调用；新增本地落盘开销单独测量 |
| 已上传交易跨终端可见 | 从平台持久确认到在线查询可见建议不超过 5 秒，读库/索引延迟计入 |
| 分页 | 默认 30 条、最大 100 条；建议值，可配置 |
| 同步与快照 | 批量、压缩、退避、抖动；Open Batch 可合并中间快照，交易结果不可丢弃 |
| 压测规模 | 初始覆盖一个 MID 100 台终端、100 万条历史记录；按真实客户规模调整 |

必须分别记录 processor 耗时、平台查询耗时、本地持久化耗时和上传积压；不能用页面首屏目标约束银行授权耗时。

## 9. 端到端验收清单

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| E2E-01 | 阻断 Paywizard 后连续本机 Sale | 正常直连收款，小票及时，记录进入待上传队列 |
| E2E-02 | 阻断 Paywizard 后对本机记录做四类后续动作 | 本地条件及通道允许时执行；不能新增平台强依赖 |
| E2E-03 | A 完成并上传后关机，B 分别处理四类动作 | A 不接收指令；B 执行，结果与原交易正确关联 |
| E2E-04 | A 未上传就离线 | B 不展示不存在的记录，也不能凭收据号构造可执行记录 |
| E2E-05 | B 缓存 A 交易后 Paywizard 故障 | 可查看缓存，禁止新发起跨终端操作 |
| E2E-06 | 本机结果成功但上传失败 | 成功状态不变；恢复后仅上传一次有效记录 |
| E2E-07 | 回传确认包丢失，同一事件重传 | 返回同一接收结果，无重复流水、重复邮件或重复统计 |
| E2E-08 | 同 eventId 提交不同金额 | 明确冲突，保留证据，不覆盖已接受内容 |
| E2E-09 | B、C 同时对 A 申请后续操作 | 平台协调冲突；processor 语义约束仍有效 |
| E2E-10 | A 与平台失联时本机操作，B 在线跨终端操作同一原交易 | 无重复完成/超额退款；必须用目标 processor 验证 |
| E2E-11 | processor 已处理但终端未收到应答 | 显示结果确认中；查单恢复，不自动重扣/重退 |
| E2E-12 | 操作 start 成功后终端崩溃 | 平台不按普通超时释放后续操作资格；恢复查证 |

| E2E-14 | 后续记录先于原交易到达 | 暂存关联待补齐，不丢弃、不创建第二条原交易 |

| E2E-16 | 终端换绑商户/MID 后残留缓存 | 不泄露旧商户缓存；旧待上传记录按原身份安全处理 |

| E2E-18 | 本机关批成功后平台故障 | 保留真实成功结果和最终批次，恢复后补传 |
| E2E-19 | 查看其他终端批次 | 只读，显示更新时间；无远程关批入口或可调用接口 |
| E2E-20 | 已关批事件先到、旧 Open 快照后到 | Closed 不回退 Open；晚到明细补齐而非重新开批 |
| E2E-21 | Refund/Capture 的 processor 批次与执行终端不一致 | 按通道确认归属，不按设备猜测；不能重复计入原金额 |
| E2E-22 | 新旧终端版本混用 | 旧记录可查；缺执行字段的记录明确仅可查看 |
| E2E-23 | 搜索、分页期间新交易持续写入 | 不重复/漏翻页，数量区分已加载与总数 |

## 11. 市场参考及使用边界

- Dejavoo 的 Settle By Store 支持在终端或 CloudPOS 选择同门店多个 TPN 关批。它说明终端上跨设备管理批次是可实现的产品模式；本期用户选择只读其他终端批次，因此不纳入远程关批。[官方说明](https://releases.ipospays.com/settle-by-store)
- Dejavoo Ticket API 使用原交易 RRN 发起预授权完成。可借鉴“稳定原交易引用”，不能据此认定 OPC 的 processor 支持跨 TID 或原终端离线。[官方接口](https://docs.ipospays.com/ipos-transact/ticket/ticket/post)
- Dejavoo SPIn USB 提供云通信不可用时的本地通信路径。可借鉴通信分层；不证明支付主机不可用时仍能在线授权，也不要求 OPC 采用 USB。[官方说明](https://docs.ipospays.com/spin-specification/spin-usb-as-fallback)
