# OPC 支付终端应用改造清单

日期：2026-09-28；版本：v1.0

关联：[总体方案](README.md) · [Paywizard 改造清单](paywizard-changes.md)

## 1. 改造边界

本文件包含两层工作：

1. **实际终端应用**：直连 processor、本地持久化、支付 SDK、打印、权限、上传与恢复。
2. **OPC_ATTD 原型**：用于表达页面、状态和流程；通过模拟服务展示双终端与平台故障场景。

两层工作不能互相代替。当前核查的 OPC_ATTD 是静态 HTML/JS 原型，sessionStorage 和 AttendedDemo 不是实际支付数据库；宿主桥接名称探测也不是已完成的原生接口。生产实现需接入实际终端工程，本文中的原生服务名为逻辑建议。

保留 Unified POS 主操作体验、现有交易渠道、金额输入、Dual Pricing 业务规则和已有操作密码。云端共享改造不要求 Vue/React 迁移，也不要求重写整个支付 SDK。

## 3. OPC-01：收款不依赖 Paywizard

需要做：

1. 保留终端直接连接 processor 的支付路径；本地生成新交易标识，不等待平台建单。
2. 检查输入金额、交易配置、SDK 初始化、商户参数、打印模板和合法操作权限是否隐含依赖平台实时请求。
3. 对既有已激活设备，本地保存执行支付所需的有效配置和安全凭据引用；刷新平台配置失败不能直接让本机收款按钮不可用。
4. 支付应答后先落本地结果与上传任务，立即呈现结果和打印，不等待平台。
5. 页面打开、Trans 刷新、同步队列和图片上传不能占用支付关键线程或阻塞刷卡。
6. 同一支付设备通常只允许一个活跃支付交互；保留 SDK 对并发读卡/支付的限制，不因新增云查询破坏它。

边界：不承诺首次未激活设备、processor 凭据已失效、设备安全策略已阻断或 processor 自身不可达时仍可完成收款。“后台离线可收款”是移除 Paywizard 依赖，不是跳过 processor 授权。

验收：断开 Paywizard 的 DNS/连接或让接口超时，重复执行本机收款仍正常；没有任何必须等平台超时后才进入支付的步骤。

## 4. OPC-02：本地持久交易与事件模型

建议在实际原生应用的持久存储中区分：

| 逻辑集合 | 用途 | 保留要求 |
| --- | --- | --- |
| local_transactions | 本机发起的交易、后续操作和原交易关联 | 不能作为普通缓存淘汰 |
| payment_intents | processor 请求前的意图、请求标识、执行阶段 | 崩溃后识别是否可能已执行 |
| payment_results | 原始结果的必要字段、查单结果及修正记录 | 只追加可审计修正，不静默覆盖事实 |
| sync_outbox | 交易/结果/批次待上传事件 | 持久化，重启可恢复，确认后才完成 |
| remote_cache | 同 MID 的远端列表和详情 | 可按范围与容量淘汰；无执行权 |
| operation_contexts | prepare/start 及本次动作上下文 | 限定设备/动作/金额，短期使用 |
| batch_snapshots | 本机 Open 快照、关批结果与历史批次 | 未上传和结果未知的批次不可清理 |
| binding_and_policy | 设备绑定、MID、权限、能力版本与配置 | 安全存储，换绑隔离 |

必要要求：

- 使用原生数据库事务或等效可靠机制。不要把生产队列保存在 sessionStorage，也不要用页面生命周期控制队列。
- 在调用 processor 前持久保存 operationId、clientTransactionId、请求指纹及可查单引用；请求标识由现有通道适配器合法生成。
- 支付结果和 outbox 事件在同一本地事务中写入；本地事件去重键在重启、页面返回、重复 SDK 回调后保持不变。
- SDK 返回到本地写入之间存在崩溃窗口，应利用 SDK 持久交易日志/processor 查单恢复，不能声称本地事务覆盖远程支付。
- 区分 originalDeviceId 与 executionDeviceId。A 的原交易被 B 下载后仍是远端记录。
- 金额采用最小货币单位整数/十进制字符串及币种精度；不使用浮点累计退款或增量授权。
- 时钟用于展示，设备序列用于本机排序，平台游标用于同步；不能靠比较两台设备的时间戳判定哪个结果更新。

验收：完成支付后强制结束应用/重启，仍可找回本机交易和待上传任务；不同设备相同收据号不冲突；B 的远端缓存不会进入“本机原交易”集合。

## 5. OPC-03、OPC-04：同步、绑定与配置

### OPC-03：上传与增量拉取

上传任务建议状态：PENDING → SENDING → ACKNOWLEDGED；临时失败回到 PENDING 并退避，永久校验错误进入 NEEDS_ATTENTION，记录仍保留。

需要做：

1. 应用启动、网络恢复、交易完成后触发同步；采用有限并发、批量上传、指数退避与抖动。
2. 上传失败只重传事件，不重新调用 processor。
3. 按每个 eventId 处理确认，允许同一批中部分成功；HTTP 200 不等于逐事件接收成功。
4. ACK 丢失时重发相同 ID 和相同内容；支付结果修正生成新事件，不能改旧 eventId 的 payload。
5. 根交易先传可减少关联等待，但仍需支持离线队列乱序及子交易先到。
6. 交易结果不可压缩丢弃；同一本机 Open Batch 的中间快照可以合并，Closed 结果不可丢弃。
7. 签名图片、邮件请求、日志等低优先级数据不阻塞核心结果上传；延续现有签名/小票服务。
8. 列表首次进入和应用回到前台时拉取变化；平台变更游标按 scope 保存，断线后续传。
9. 暂停/重启/升级后恢复队列；不能因重新登录、切换 MID 或清缓存丢失未上传记录。
10. 记录最近成功同步时间、积压数量、最老事件时间与错误类别，供设置页/诊断查看。

建议优先级：结果核实及后续操作结果、普通交易结果、已关批结果、Open 快照、图片/日志；优先级不能破坏事件依赖和批次明细完整性。

### OPC-04：设备绑定与 MID 范围

- 以本机已激活收单配置确定当前 MID；多 MID 设备切换时同步切换查询、缓存、权限与支付配置，不能只换 UI 标签。
- deviceId/SN、MID/TID、processor/环境、账户和绑定版本完整传入可信原生数据层。
- 缓存按 tenant + acquiringAccount + MID + 绑定范围分区，避免同 MID 字符串混用。
- 换绑后停止暴露旧范围缓存；旧待上传事件仍按原绑定处理，通过保留的合法身份或受控恢复流程回传，不能重签为新商户记录。
- Paywizard 凭据失效时暂停云查询/跨终端操作，提示恢复认证；不应把它自动转成 processor 凭据失效。

验收：换绑和 MID 切换均不泄漏交易；平台凭据刷新失败不会阻断仍合法的本机支付链路。

## 6. OPC-05：Trans 列表

### 6.1 默认行为与筛选

- 默认范围：当前 MID → All terminals；日期建议为业务当地今天，可选择日期范围。
- 快速切换 This terminal，必要时选具体终端；范围显示在列表上方，避免误以为只查本机。
- 沿用已有搜索入口，支持收据号、后四位、金额和日期等；不用额外建立一套独立“云交易 App”。
- 返回列表时保留终端/日期/类型筛选、搜索词与滚动位置。
- 更多历史按页加载；“当前 MID 所有交易”不等于仅今日，也不等于全量下载。

### 6.2 列表字段与状态

主行保留类型、金额、时间、支付状态；次行显示 Terminal Name/TID、收据号/必要卡信息。当前设备可标记 This terminal；信息保持适合终端屏幕的密度。

建议 UI 状态：

| 状态 | 展示与动作 |
| --- | --- |
| 首次加载无缓存 | 骨架/加载提示，可返回本机收款，不阻塞主界面 |
| 已有缓存正在刷新 | 先显示列表及更新时间，后台刷新 |
| 平台不可达 | 显示 Cached / Last updated；提供 This terminal |
| 本机支付成功未上传 | 支付仍为 Approved，辅以 Pending sync |
| processor 结果未知 | Result pending；不可显示支付失败或退款成功 |
| 搜索无结果 | 说明当前范围/日期下无匹配；不以接口错误冒充空结果 |
| 部分分页失败 | 保留已加载数据，提供重新加载 |

### 6.3 合并规则

1. 云端记录按 transactionId，与本机 clientTransactionId 的映射去重；映射在上传 ACK 时持久保存。
2. 本机未上传记录可以合并进当前筛选范围，并标记待同步；不得将本机数量相加为全 MID 的准确总数。
3. 远端快照比本机已确认操作旧时，保留本机最新事实并等待平台合并，不能覆盖回旧状态。
4. 当前 MID/日期变更后只读取匹配缓存，不短暂展示前一商户的数据。

验收：A/B 两台设备的交易均可见；同收据号可区分；本机刚完成交易不会等上传后才出现，也不会上传后出现两次。

## 7. OPC-06、OPC-07：详情与后续操作

### OPC-06：统一详情数据源

无论来自 Trans、按收据号查找、卡号查找、Capture 寻单或 Reprint，都通过同一交易仓库读取详情。

详情展示：

- 原交易类型、原金额、币种、支付结果、时间、原终端与收据。
- 关联 Refund、Void、Capture、Auth-Incremental 的时间、金额、执行终端及结果。
- 当前授权金额、已完成/已退金额等适用信息；无法确认的值明确待更新。
- 所属批次、平台更新时间、本机待同步/结果待核实状态。
- 按当前动作资格呈现按钮及不可用原因。

未知 ID 应显示“交易不存在或无权限”，不能回退到样例交易。列表弹窗详情与独立详情页必须共用相同模型，避免看到不同金额或状态。

### OPC-07：四种后续动作分别适配

| 动作 | 输入与展示 | 必须校验的条件 | 必须保留的结果 |
| --- | --- | --- | --- |
| Refund | 原付款、可退金额、本次退款金额；按通道允许部分退款 | 原付款引用、累计已退/未决、币种、是否需再读卡 | 独立退款记录、原付款关联、实际退款金额和批次 |
| Void | 明确要撤销哪一笔 Sale/Refund/Capture/PreAuth（按通道支持） | 原交易类型、当前状态、结算窗口；不能只判断“B 当前批次” | 独立撤销事实及被撤销记录，不修改原金额 |
| Capture | 选择 OPEN AUTH，输入本次完成金额 | 最新授权、是否支持部分/多次 Capture、是否允许超授权金额 | Capture 记录和实际批准金额，关联原 PreAuth |
| Auth-Incremental | 明确“本次增加金额”与“增加后授权总额” | 原授权状态、增量次数/金额/有效期等通道规则 | 每次增量记录及最新批准授权总额 |

以上金额能力由通道控制；原型中“超授权弹警告后可继续”不能直接变成生产规则。

从交易详情发起的 Refund 是关联原交易退款。已有按金额进入的独立 Refund/现金退款入口保持原业务边界，不能默默把两类操作合并或让关联卡退款自动改退现金。

验收：四类动作的原交易与执行终端明确；操作金额与 processor 报文一致；取消返回正确详情；已有收款/现金/Dual Pricing 规则不随此次改造变化。

## 8. OPC-08、OPC-09：跨终端执行

### OPC-08：本地执行状态机

建议阶段：SELECTED → PREPARING → PREPARED → START_CONFIRMING → DISPATCHING → APPROVED/DECLINED/UNKNOWN → RESULT_PENDING_SYNC/SYNCED。

需要做：

1. 判断是本机还是跨终端，依据不可变的原交易设备身份；在本地缓存中找到记录不改变分类。
2. 跨终端执行前必须连接平台，刷新详情、检查权限及已有 Manager PIN，调用 prepare。
3. operationId 在 prepare 前落本地；重复点击、页面返回、重启恢复均使用相同 ID。
4. prepare 成功后保存上下文，start 获得确认后才允许发送 processor；原生层再次验证动作、金额、币种、设备和期限。
5. prepare/start 失败或平台在发送前已不可用时，不发起跨终端资金请求；不能降级为本机路径。
6. start 确认后即使平台在实际发出请求时恰好断开，也只能按“可能已执行”处理；分布式网络不能保证两个远端动作同时完成。
7. processor 已发出后平台故障，不中断结果收集，不再次发起同一动作；落本地并等待补传。
8. 本机操作在线时可以尽力登记/更新平台，已知该交易有未决操作时先查明；平台不可用本身不是本机操作阻断条件。
9. prepare 返回 STATE_CHANGED 时展示更新后的金额/状态，由用户重新确认，不自动按新金额执行。

若 prepare 已成功但未 start，用户取消应释放平台登记；若 start 已确认且应用崩溃，恢复后按 UNKNOWN 查证，不依据界面未出现成功页判断未支付。

### OPC-09：processor 适配器

每种 processor 至少完成以下映射与测试：

| 项目 | 要求 |
| --- | --- |
| 原交易定位 | 映射 processorTransactionId/RRN/STAN/原日期等必需字段；不能靠后四位/收据号定位资金交易 |
| 原始与当前 TID | 明确 originalTid 与 executionTid；不盲目复制 A 的凭据，也不随意改成 B |
| 安全支付引用 | 只使用通道批准的可跨设备引用/token；不可共享 A 的设备密钥或完整敏感卡数据 |
| 当前动作 | 逐项验证 Refund/Void/Capture/Incremental 的报文、金额方向和状态窗口 |
| 幂等与查单 | 同一业务操作保持通道允许的稳定请求引用；独立 operationId 不自动等于 processor 幂等键 |
| 重试 | 已发送后先查单；只有明确未执行且符合通道规则才允许重新发送 |
| 并发语义 | 验证不同操作 ID 同时退款/完成/撤销时，processor 如何防止不合法结果 |
| 结果与批次 | 保存实际批准金额、响应码、结果引用及真实批次归属 |

能力不足的通道保留查询和本机既有能力，跨终端相关按钮显示不可执行原因。不能为了让所有按钮可点而假设通道支持。

## 9. OPC-10、OPC-11：结果、小票与恢复

### OPC-10：记录支付事实

- 每次后续操作保存独立记录，并关联原交易和 root；执行终端 B 不覆盖原交易终端 A。
- 成功后立即展示真实结果，支付小票按 processor/现有认证模板打印；平台待同步仅作为附加状态。
- Reprint 使用保存的真实结果与小票信息；不因重打小票重复执行支付、重复创建业务记录。
- A 恢复同步时接收 B 已发生的后续操作，用于显示与后续校验。不能直接修改 SDK 的内部账或批次文件，应通过 SDK 支持的刷新/查单机制对齐。
- B 若得到属于 A 或其他通道结算范围的批次号，记录其真实关联；不自动把该金额计入 B 本机 processor 批次。
- 平台回传确认丢失，只重传事件。小票已经打印不作为上传成功证明。

### OPC-11：超时和崩溃恢复

| 故障点 | 恢复要求 |
| --- | --- |
| 请求意图保存前 | 不得发支付请求 |
| 意图已保存，确定未发请求 | 可恢复输入/取消；跨终端需重新验证准备状态 |
| start 响应丢失 | 查询同一 operationId 的平台状态，不新建另一笔操作 |
| 请求已发送，应答丢失 | 标记 UNKNOWN，按原请求引用查 processor |
| SDK 收到结果，应用写库前崩溃 | 从 SDK 持久日志/processor 查单恢复，不能凭缺少应用记录判失败 |
| 结果已保存，平台上传前崩溃 | 从 outbox 继续上传 |
| 平台收到结果但 ACK 丢失 | 同 eventId 重传，接收重复确认 |
| result 已上传但原交易尚未到平台 | 保留确认与等待关联信息，继续上传父记录，不创建另一条父交易 |

查单 not-found 是否足以证明未执行，由具体 processor 的时效与协议决定。未知操作不能在应用重启时一律转失败。查单可能也不可用时，明确待核实并保留证据，不让收银员通过重复刷卡“试试看”。

验收：断网、杀进程、重启、SDK 回调重复、平台响应丢失等故障注入后，没有重复资金请求或丢失的已成功记录。

## 10. OPC-12：Batch Reports 与 Close Batch

### 10.1 页面调整

Batch Reports 默认本机，增加 All terminals/具体终端筛选；各终端可看 Open 与 Closed 历史批次。Open 数据须来自终端主动上传的快照，不能只依赖现有结算成功回传。

列表字段建议：Terminal Name/TID、Batch No、Open/Closed、币种、笔数、金额、Last updated。详情增加汇总与明细完整性说明。

Close Batch 仅本机可用：

- 他机详情不显示关批按钮；原生调用层也校验目标设备，不能只靠 UI 隐藏。
- 本机关批沿既有 PIN 和 processor 流程执行，Paywizard 故障不阻止。
- 未完成 PreAuth 是否跨批保留由实际通道确认；不能把原型的继续按钮当为所有通道通用。
- processor 返回未知结果时显示待确认，禁止直接生成“成功关批”的 Settlement Copy。

### 10.2 快照生成和上传

1. 每个真实批次生成并持久保存 batchUid、processorBatchNumber、代次和归属。
2. 交易成功、退款/撤销/完成、重启恢复、关批结果等事件触发快照；Open 快照节流合并，不每条明细都发全批。
3. 关批保存最终摘要与明细集合；大批次分块上传，块 ID/版本保持稳定。
4. 新批次不能覆盖旧批次的待上传数据；批次号循环使用时有新代次标识。
5. 收到平台完整确认后，按既有留存策略归档；不能为释放空间删除未确认结果。
6. 当前本机汇总、云端他机快照、processor 确认关批结果分别标识，避免把三者混为实时一致。

验收：断开平台后仍可完成本机关批并打印真实结果；恢复后他机可查；迟到旧快照不覆盖关批记录；不同终端相同批次号不冲突。

## 11. OPC-13、OPC-14：权限与故障体验

### OPC-13：权限和 Manager PIN

保留 Void、Refund、Close Batch 的独立配置语义，包括现有“未配置则不要求”的业务规则；实际凭据在受信原生层安全保存和验证。跨终端不是每次新增经理审批，但执行人/设备仍需对应操作权限。

不能把生产 PIN 放入网页 localStorage，不能通过修改 URL 参数或 JS 布尔值绕过。UI 只拿验证结果句柄；原生层负责将验证与当前操作绑定。已有人员身份则记录实际人员，无个人登录时明确记录设备及授权方式。

远端执行上下文按动作短期保存，退出/失效后销毁不再需要的敏感内容；审计及必要原交易引用按既有安全要求保留。

### OPC-14：可理解的降级

至少区分：Paywizard 可用性、processor 连接、设备本地待同步状态。设备连着 Wi-Fi 不表示 Paywizard 可用；Paywizard 不可用也不等于不能收款。

推荐提示：

| 场景 | 提示含义 |
| --- | --- |
| 平台查询失败 | 云端记录暂时无法更新，可以继续本机收款 |
| 本机成功待上传 | 支付成功，记录待同步 |
| 跨终端动作未能准备 | 需要连接 Paywizard 才能处理其他终端交易 |
| 远端批次缓存 | 显示最近更新时间，当前为缓存数据 |
| processor 结果未知 | 正在确认交易结果，请勿重复发起 |

恢复连接后自动补传并刷新当前页面，不强制跳转、不打断正在输入或正在支付的流程。整页遮罩或长时间转圈不得锁住 Unified POS。

## 12. OPC-15：性能与本地资源

- UI 和键盘本地渲染；网络同步、JSON 处理、图片与日志上传放后台。
- 数据列表分页和按需详情；缓存近期远端记录，不复制整个 MID 多年历史。
- 同步上传批量大小、并发、退避、查询超时可配置；数值结合实际机型/网络测试，不写死为产品保证。
- 缓存淘汰优先远端已确认记录；未上传本机交易、UNKNOWN 操作、未完成授权等不得作为普通缓存清理。
- 存储压力提前告警；若无法可靠保存支付意图，按现有设备故障规则停止新请求，不能假装安全地无限收款。
- 当前页面离开后取消无用查询，但不能取消已经发出的支付或丢弃待上传结果。
- 记录本地展示、processor、落盘、平台查询、上传各阶段耗时，定位真实慢点。

验收目标沿用总体方案第 8 节；性能测试必须包含平台慢响应和积压恢复，不只测试正常 Wi-Fi。

## 13. OPC-16：实际代码与原型接线

### 13.1 实际终端的建议逻辑模块

以下为职责划分，可在现有工程内实现，不要求另起应用或更换技术栈。

| 模块 | 职责 |
| --- | --- |

| ReceiptService | 支付小票、Settlement Copy、Reprint，与支付执行解耦 |

### 13.3 原型与真实桥接建议

对 UI 暴露稳定接口，例如 queryTransactions、getTransaction、prepareOperation、executeOperation、getOperationStatus、getBatches、closeLocalBatch、reprintReceipt。

- Demo 适配器提供模拟结果，不接真实 processor。
- Native 适配器调用真实原生服务；executeOperation 内部保证状态、权限和请求发送次序。
- 生产构建中不存在宿主时明确报功能不可用，不能自动退回模拟成功。
- 所有异步结果绑定 requestId/operationId，迟到回调不能覆盖用户当前查看的另一笔交易。
- 页面 URL 只携带非敏感记录 ID；执行上下文保存在受信层，不能放在 URL/localStorage。

### 13.4 灰度与回滚

先启用可靠回传，再开放只读查询与批次查看，最后按 processor/动作启用跨终端执行。开关关闭后保留本机支付和结果恢复；历史 UNKNOWN、outbox、批次上传任务继续处理。

原型演示可先上线，但发布说明必须明确模拟范围；不能把浏览器双终端样例视为真实跨终端支付已经完成。

## 14. OPC-17：测试、诊断与交付

### 14.1 必须交付

1. 本地数据模型及升级策略，包含旧交易迁移和远端缓存隔离。
2. 原生桥接/SDK 接口文档与各 processor 的原交易字段映射。
3. 四类后续交易支持矩阵、查单/重试规则和批次归属证据。
4. Trans、详情、后续交易、Batch Reports、故障降级的原型与真实应用截图/录屏。
5. 故障注入记录：平台断开、processor 超时、断电/杀进程、重复回调、乱序回传、换绑与回滚。
6. 本机可导出的脱敏诊断：operationId、eventId、阶段、时间、通道结果码、同步状态；不导出敏感支付凭据。

### 14.2 测试分层

| 层级 | 可以证明 | 不能代替 |
| --- | --- | --- |
| OPC_ATTD 原型 | 页面、文案、按钮边界、模拟状态切换 | 本地可靠持久化、真实支付、权限与硬件打印 |
| 原生/接口联调 | outbox、幂等、认证、prepare/start/result、缓存与恢复 | 实际通道对跨设备请求的支持 |
| processor 测试环境/认证 | 原交易引用、并发、金额、超时、批次及设备约束 | 目标生产机型和部署环境验收 |
| 实机试点 | 实际网络、打印、升级、持续运行和性能 | 未启用的其他通道/机型 |

详细场景按总体方案 E2E-01 至 E2E-26 执行；用 A、B、C 至少三台逻辑/真实设备覆盖并发，不能只在同一设备两个页面中演示。
